# Product Specification

## Feature
- Feature ID: `m3-agent-cta`
- Title: Agent CTA Suggestions — Context-Aware Action Cards After Agent Replies

## Background

The M3 agent-chat line has built a collaborative chat surface where humans and the Hermes agent
co-author feature artifacts through conversation:

- **v1–v3** — streaming chat, session history, document authoring, approval gating
- **v4** — multi-member threads, channels, `@mention`-triggered dispatch

In every version, the conversation moves forward by the human typing a new message. The agent
never hints at what a natural next step would be — the user must know the available commands,
the current lifecycle stage, and the right follow-up to ask. This creates unnecessary friction,
especially for new users, and slows down the feature-authoring loop for everyone.

## Problem

### Users don't know what to do after an agent reply

After the agent responds — whether it wrote a product spec, explained a technical decision, or
ran a lifecycle action — the conversation stalls. The user must mentally map the current stage
to the right next action (e.g. "I should now approve the spec"), remember the exact command
syntax (e.g. `/approve-product-spec`), and type it. Experienced users do this fluently; new
users get stuck or take the wrong path.

### No affordance surfaces available lifecycle actions

The chat input is a blank text box with no in-context guidance. The set of valid next actions
changes per feature stage and per conversation turn, but the UI never reflects this. The only
escape is reading documentation or trial-and-error with slash commands.

### Momentum is lost between turns

Each round-trip through the agent loop — type a command, wait for the response, think about
what to do next — breaks the flow of feature development. A visible, clickable hint that
represents the most natural follow-up action would compress the thinking step and keep the
user moving.

## Goals

- **G1 — Context-aware CTA cards after agent replies.** After every agent response, render
  1–3 CTA suggestion cards below the reply bubble. Cards are generated by the agent alongside
  its reply and reflect the most relevant next actions given the current conversation and
  feature lifecycle state.
- **G2 — One-click submission.** Clicking a CTA card immediately submits its action text as
  the user's next message — no typing required. The card's action is a plain-text prompt or
  slash command (e.g. `/approve-product-spec`).
- **G3 — Structured card format.** Each card shows: a short title, a category label, an icon,
  a one-sentence description of what will happen, and a primary action button. Cards do not
  expose raw command syntax to the user — the button label uses natural language.
- **G4 — Agent-generated, not hardcoded.** The agent produces CTA suggestions as structured
  output delivered alongside the main reply. Suggestions reflect the actual content of the
  conversation — they can be follow-up questions, lifecycle actions, risk checks, or any other
  contextually appropriate next step.
- **G5 — Optional, not required.** The agent may return zero CTAs when no clear next step
  exists. The user can always type freely; CTAs are shortcuts, not guardrails.
- **G6 — Works across all M3 chat surfaces.** CTA cards appear in feature-thread sessions,
  workspace-level team threads, and channels — any surface that hosts an agent response.
- **G7 — Conversation-start suggestions.** When a thread or session opens with no prior
  messages, a set of starter CTA cards is shown in the empty-state area above the composer.
  These are derived from the current feature lifecycle state (e.g. `in_design` → "Write product
  spec") and available agent capabilities (e.g. "Search codebase with GitNexus", "Query RAG").
  They disappear once the first message is sent.

## Non-goals

- **NG1 — No multi-step CTA flows.** A CTA click sends a single message. There is no wizard,
  multi-step form, or sub-prompt sequence launched from a card click.
- **NG2 — No user-authored custom CTAs.** Users cannot create or save their own CTA templates
  in this iteration.
- **NG3 — No CTA persistence across sessions.** CTAs are ephemeral per agent turn — they do
  not persist in history as interactive elements. Past turns display CTAs as static, non-
  clickable cards (grayed out) to preserve the visual record without implying they can still
  be acted on.
- **NG4 — No approval gate bypass.** A CTA card that triggers a lifecycle action (e.g.
  `/approve-product-spec`) submits the command as a user message; the agent then executes the
  approval with the same human-gating logic already in place. CTAs are input shortcuts only —
  they do not bypass any workflow permission model.
- **NG5 — No CTA editing before submission.** Clicking a CTA submits its action text as-is.
  Pre-submission editing of CTA text is not in scope.

## User Experience

### CTA card anatomy

Each card contains:
- **Icon** — a small emoji or icon indicating the action category
- **Title** — 2–5 word action name (e.g. "Approve product spec", "Ask follow-up", "Check invalidation")
- **Category tag** — short label identifying the action type (e.g. "Lifecycle", "Clarify", "Risk")
- **Description** — one sentence describing what will happen when the user clicks (e.g. "Mark the current product spec approved and move to technical design")
- **Action button** — primary button with label and arrow (e.g. "Approve →", "Ask →")

### Placement

CTA cards appear directly below the agent response bubble, before the message composer. Up to
three cards render in a horizontal row on desktop. On mobile/narrow viewports, cards stack
vertically. The cards fade in after the agent response finishes streaming.

### Click behavior

Clicking a card's action button:
1. Clears any draft in the message composer
2. Submits the card's action text as the user's next message
3. Dismisses / grays out the CTA row immediately (same visual as past-turn cards)
4. The conversation continues normally from the submitted message

### Past-turn cards

CTA cards from completed turns are rendered as visually inert cards — same layout but with
disabled buttons and reduced opacity. They record what was suggested without implying
interactivity.

### Conversation-start (empty-state) suggestions

When a thread or channel opens with no prior messages, the empty-state area displays 2–4
starter CTA cards. These are determined by the frontend from two sources — no agent call needed:

1. **Feature lifecycle state** — resolved from the current feature's `status.yaml`. The UI
   maps each stage to one or two canonical action cards:

   | Stage | Starter card(s) |
   |---|---|
   | `in_design` — no spec yet | "Write product spec" |
   | `in_design` — spec exists | "Approve product spec", "Revise product spec" |
   | `in_tdd` | "Write technical design", "Approve technical design" |
   | `ready_for_implementation` | "Generate task breakdown" |
   | `in_implementation` | "Check task status", "Review a PR" |
   | Channel / no feature context | (capability starters only) |

2. **Available agent capabilities** — a fixed set of capability starters shown when the
   relevant tool is configured (resolved from workspace settings):

   - **"Write product spec"** — `action_text: "/write-product-spec"`
   - **"Search codebase (GitNexus)"** — `action_text: "Search the codebase for ..."` (opens with cursor in composer, pre-filled)
   - **"Query knowledge base (RAG)"** — `action_text: "Search the knowledge base for ..."`
   - **"Summarise recent changes"** — `action_text: "/summarise-recent-changes"`

   Capability starters for tools that are not configured are hidden (e.g. GitNexus starter is
   suppressed when `GITNEXUS_MCP_URL` is absent from the environment).

Starter cards use the same card anatomy as post-reply CTAs. They are dismissed as soon as the
user sends any message or clicks a card.

### Examples

On conversation start (feature in `in_design`, no spec written yet):
- **[Write product spec →]** (Lifecycle) — "Draft the product spec for this feature with the agent."
- **[Search codebase →]** (GitNexus) — "Find relevant code or symbols before starting design."
- **[Query knowledge base →]** (RAG) — "Search indexed docs and prior decisions for context."

On conversation start (feature in `in_design`, spec already drafted):
- **[Approve product spec →]** (Lifecycle) — "Mark the spec approved and advance to technical design."
- **[Revise product spec →]** (Lifecycle) — "Ask the agent to update the existing draft."

After the agent writes a product spec:
- **[Approve product spec →]** (Lifecycle) — "Mark the spec approved and advance the feature to technical design."
- **[Request changes →]** (Feedback) — "Ask the agent to revise the spec based on your notes."

After the agent writes a technical design:
- **[Approve technical design →]** (Lifecycle) — "Approve the design and generate the task breakdown."
- **[Stress-test the design →]** (Review) — "Ask the agent to identify risks and gaps in the proposed approach."
- **[Revise a section →]** (Edit) — "Direct the agent to rewrite a specific section of the design."

After the agent answers a question mid-conversation:
- **[Go deeper →]** (Clarify) — "Ask the agent to expand on the last point."
- **[Apply this to my spec →]** (Action) — "Incorporate the agent's last answer into the draft."

## Technical Overview

### CTA delivery

The agent generates CTA suggestions as a structured JSON object attached to the agent turn
response — not as a separate API call. The BFF receives the main message content and an
optional `cta_suggestions` field in the agent turn payload. This keeps suggestions latency-
bound to the main response with no additional round-trip.

```
agent turn payload:
{
  "content": "...",         // streamed markdown
  "cta_suggestions": [      // optional; present only when agent decides CTAs are useful
    {
      "id": "cta-1",
      "title": "Approve product spec",
      "category": "Lifecycle",
      "description": "Mark the spec approved and advance to technical design.",
      "action_text": "/approve-product-spec",
      "button_label": "Approve"
    },
    ...
  ]
}
```

### Frontend rendering

The `digital-factory-ui` receives `cta_suggestions` via the existing chat SSE/WebSocket stream
as a terminal event after the main content finishes. The UI renders the cards after the stream
closes. Past-turn cards are stored in message history and rendered as disabled on re-render.

### Agent-side generation

The Hermes agent prompt is extended with instructions to produce CTA suggestions when a natural
next step exists. A lightweight structured output schema ensures the agent always returns valid
card data or an empty array. CTA generation is part of the agent's normal turn; no additional
model call is made.

## Acceptance Criteria

- **AC1** — After an agent response that includes `cta_suggestions`, 1–3 CTA cards render below
  the agent bubble before the next composer interaction.
- **AC2** — Clicking a card's action button submits its `action_text` as the user's next message
  with no additional typing required.
- **AC3** — After a CTA is clicked, the CTA row becomes visually inactive (disabled buttons,
  reduced opacity) within one render cycle.
- **AC4** — Past-turn CTA cards are displayed as inert (non-clickable) when scrolling through
  conversation history.
- **AC5** — When the agent returns zero CTAs, no card row appears and the UI degrades gracefully.
- **AC6** — CTA cards render correctly in feature-thread sessions, workspace channels, and
  team threads.
- **AC7** — On mobile/narrow viewports (< 768px), cards stack vertically without horizontal
  overflow.
- **AC8** — The CTA row fades in only after the agent response finishes streaming, not mid-stream.
- **AC9** — When a thread or session opens with no prior messages, 2–4 starter CTA cards are
  shown in the empty-state area above the composer.
- **AC10** — Starter cards reflect the current feature lifecycle stage (resolved from
  `status.yaml`) and the available agent capabilities (GitNexus, RAG suppressed when not
  configured).
- **AC11** — Starter cards are dismissed immediately when the user sends any message or clicks
  a card — they do not persist into the conversation history as interactive elements.
