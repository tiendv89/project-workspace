# Product Specification

## Feature

- Feature ID: `workspace-tabs-chat`
- Title: `Workspace Tabs, Work Item Tabs, and Agent Chat`

## Problem

Users need to move between a workspace board, saved workspaces, feature detail sessions, task detail sessions, and scoped agent conversations without losing their place. The dashboard currently needs a clearer tab model: the workspace tab should always return the user to the board, task and feature tabs should preserve deep work sessions, and agent chat should follow the active task or feature context.

This feature defines the expected user journeys for workspace switching, workspace import, task tabs, feature tabs, and task/feature-scoped agent chat. It also clarifies that chat is UI-only for now: the UI prepares the correct context, but does not generate mock agent responses before a real chat API exists.

## Goals

- Let users return to the current workspace board by clicking the workspace tab.
- Let users open a workspace switcher from the workspace tab dropdown control.
- Let users search saved workspaces and switch to another workspace.
- Let users import a new workspace from a GitHub repository URL and GitHub token.
- Let users inspect tasks and features quickly with single click.
- Let users open persistent task tabs and feature tabs with double click or context menu actions.
- Ensure feature double click opens a feature tab only in Feature Mode.
- Hide the sidebar when a task tab or feature tab is active.
- Let users inspect task metadata, task activity, PR state, feature source documents, feature tasks, and feature logs inside work item tabs.
- Let users open agent chat only from task or feature context.
- Let users create new scoped chat sessions, choose a model, use skill mentions, paste image attachments, resize chat, and expand chat.
- Prepare the scoped task or feature context for a future chat API without using mock responses.

## Non-goals

- No workspace-scope agent chat in this feature.
- No real backend or LLM chat response API is introduced by this product spec.
- No mock assistant responses should be generated by the chat UI.
- No workflow lifecycle, approval gate, task status, or task YAML ownership rule changes.
- No broad dashboard redesign outside workspace tabs, work item tabs, and scoped chat.
- No creation of `deployment-checklist.md` at this stage.

## Definitions

### Workspace tab

The workspace tab is the primary header tab for the active workspace. Clicking the workspace tab returns the user to the workspace board. The workspace switcher opens only from the dropdown control on the workspace tab.

### Work item tab

A work item tab is a persistent detail session opened from a task or feature.

Supported work item tab types:

- `Task tab` - a task detail session.
- `Feature tab` - a feature detail session.

Work item tabs sit in the same header area as the workspace tab. They let the user switch between the board, task sessions, and feature sessions without closing context.

### Agent chat

Agent chat is a right-side chat panel scoped to the active task or feature. It is not available as a standalone workspace-board chat. For now, the chat layer prepares UI state and scoped context only; it does not call a real LLM API or create fake assistant responses.

## User Journey

### Journey 1 - Return from a work item tab to the workspace board

1. The user is inside a task tab or feature tab.
2. The user clicks the workspace tab in the header.
3. The app returns to the Kanban board for the current workspace.
4. The workspace tab becomes active.
5. The previously active task or feature tab remains available in the header.
6. Any quick-view modal or sheet is closed or no longer the primary focus.

Expected result: the user returns to the board without closing open task or feature tabs.

### Journey 2 - Open the workspace switcher

1. The user is on the dashboard with at least one saved workspace.
2. The user clicks the dropdown control on the workspace tab.
3. A dropdown opens below the workspace tab with the title `Switch workspace`.
4. The search input is focused automatically.
5. The dropdown lists saved workspaces.
6. Each workspace item shows:
   - Workspace initials or avatar.
   - Workspace name.
   - Repository URL when available.
   - Role or descriptive metadata when no repository URL is available.
   - A check indicator for the active workspace.
7. The footer shows an `Import workspace` action.

Expected result: the user can immediately search, select another workspace, or start importing a workspace.

### Journey 3 - Search saved workspaces

1. The user opens the workspace switcher.
2. The user types into the `Search workspaces...` input.
3. The list filters immediately by workspace name or related metadata.
4. If matches exist, only matching workspaces are shown.
5. If no matches exist, the dropdown shows `No workspace matches this search.`

Expected result: the user can find and open a saved workspace quickly.

### Journey 4 - Switch to another workspace

1. The user opens the workspace switcher.
2. The user clicks a different workspace.
3. The switcher closes.
4. The app loads the selected workspace board.
5. The workspace tab shows the new workspace name.
6. The active tab resets to the workspace board.
7. Task and feature tabs from the previous workspace are not shown in the new workspace.
8. Board filters, search state, sidebar state, and scoped chat context update for the selected workspace.

Expected result: the selected workspace becomes active and the user starts from that workspace board.

### Journey 5 - Close the workspace switcher without switching

1. The workspace switcher is open.
2. The user clicks outside the switcher or presses Escape.
3. The switcher closes.
4. The search query resets.
5. The active workspace does not change.

Expected result: the dashboard returns to its previous state with no workspace change.

### Journey 6 - Start importing a workspace

1. The user opens the workspace switcher.
2. The user clicks `Import workspace`.
3. The switcher closes.
4. An `Import workspace` modal opens directly to the import form.
5. The modal does not show saved workspace selection.

Expected result: the user reaches the import form without an extra selection step.

### Journey 7 - Fill the import workspace form

1. The modal title is `Import workspace`.
2. The description is `Import a repository to create a new workspace.`
3. The body shows a `Repository` form section.
4. The user enters a required `Repository URL`, such as `https://github.com/owner/repo`.
5. The user enters a `GitHub Personal Access Token` in a password-style input.
6. The token is not displayed back to the user after entry.
7. The `Import workspace` submit action is disabled while the repository URL is empty.

Expected result: the user can provide the repository identity and access token needed to create a workspace.

### Journey 8 - Import workspace successfully

1. The user enters a supported repository URL.
2. The user enters a GitHub token when needed.
3. The user clicks `Import workspace`.
4. The app validates that the URL is present, supported, and not already imported.
5. The app attempts to access the repository.
6. If the import succeeds, the workspace is added to the saved workspace list.
7. The modal closes.
8. The user can switch to the imported workspace from the workspace switcher.

Expected result: the imported workspace is available as a saved workspace.

### Journey 9 - Import workspace fails

1. The user submits the import form.
2. The import fails because the URL is empty, the URL format is unsupported, the workspace already exists, the token is missing required access, or repository access fails.
3. The modal stays open.
4. A clear error appears under the form or near the affected input.
5. The user edits the repository URL or token.
6. The current error clears so the user can retry.

Expected result: the user can correct the import input without losing form context.

### Journey 10 - Close the import workspace modal

1. The import modal is open.
2. The user clicks the close button or the backdrop.
3. The modal closes.
4. Repository URL, token, and error state reset.
5. No workspace is imported.
6. The active workspace remains unchanged.

Expected result: closing the modal leaves the dashboard unchanged.

### Journey 11 - Single click a task on the board

1. The user is in Task Mode on the workspace board.
2. The user single-clicks a task card.
3. The app opens a task quick-view modal or sheet immediately.
4. The detail view shows task title, task ID, parent feature, status, priority when available, actor type when available, next action, blocked reason when available, and related execution or handoff metadata when available.

Expected result: the user can inspect a task quickly without creating a tab.

### Journey 12 - Double click a task on the board

1. The user is in Task Mode on the workspace board.
2. The user double-clicks a task card.
3. The app opens or focuses the task tab for that task.
4. The header shows a `T` indicator and the label `taskId - taskTitle`.
5. If the task tab already exists, the app focuses the existing tab instead of creating a duplicate.

Expected result: the user enters a persistent task work session and can return to the board by clicking the workspace tab.

### Journey 13 - Right click a task on the board

1. The user right-clicks a task card.
2. The browser context menu does not appear.
3. A custom context menu opens at the pointer location.
4. The menu shows `New tab`.
5. The user clicks `New tab`.
6. The app opens a task tab for that task.
7. The context menu closes.

Expected result: the user has a clear context-menu path to open a task tab.

### Journey 14 - Use task items from the sidebar

1. The user is on the workspace board, where the sidebar is visible.
2. The sidebar shows task groups such as `IN PROGRESS`, `IN REVIEW`, and `READY`.
3. The user single-clicks a task item.
4. The app opens the task quick-view modal or sheet.
5. The user double-clicks a task item.
6. The app opens or focuses the task tab.
7. The user right-clicks a task item and chooses `New tab`.
8. The app opens a task tab from the sidebar context.

Expected result: sidebar task items behave consistently with task cards on the board.

### Journey 15 - Single click a feature in Task Mode

1. The user is in Task Mode on the workspace board.
2. The board shows feature rows with task-level information.
3. The user single-clicks the content area of a feature row.
4. The app opens a feature quick-view modal or sheet.
5. The quick view shows feature title, feature ID, status, summary or description when available, last modified time when available, source documents when available, and task or progress summary when useful.
6. Double-clicking a feature row in Task Mode does not open a feature tab.

Expected result: the user can inspect feature information quickly while staying on the task-level board.

### Journey 16 - Switch to Feature Mode

1. The user clicks the `Feature` mode toggle.
2. The board changes from task-level view to feature-level view.
3. Task cards and task rows are hidden.
4. Feature-mode search and filters apply independently.
5. The board shows feature rows or cards by feature status.

Expected result: the user can scan feature-level state without task-level noise.

### Journey 17 - Open a feature tab in Feature Mode

1. The user is in Feature Mode.
2. The user single-clicks a feature.
3. The app opens a feature quick-view modal or sheet.
4. The user double-clicks a feature.
5. The app opens or focuses the feature tab for that feature.
6. If the feature tab already exists, the app focuses the existing tab.
7. The user can also right-click the feature and choose `New tab`.

Expected result: Feature Mode supports quick inspection and deep feature work sessions.

### Journey 18 - Activate a task tab

1. A task tab exists in the header.
2. The user clicks the task tab.
3. The task tab becomes active.
4. The main content changes to the task detail session.
5. The workspace board is no longer active.
6. The sidebar is hidden.
7. If agent chat is open, chat scope follows the task.

Expected result: the user returns to the exact task session represented by the tab.

### Journey 19 - Read task tab content

1. The user opens a task tab.
2. The task tab header shows:
   - Back action.
   - Task title.
   - Copy task ID action.
   - Task ID badge.
   - Status badge.
   - Priority badge when available.
   - Updated time when available.
   - Agent chat open action when chat is closed.
3. The user reads task information blocks:
   - Repository, or `None`.
   - Branch, or `None`.
   - Next Action, or `None`.
   - Executed By: `Agent`, `Human`, or `Unassigned`.
   - Depends On, or `None`.
   - Blocked Reason when present.
   - Blocked Context, or `None`.
4. The user reviews the `Pull Requests` section for workspace PR and repository PR state.
5. PR items with URLs are clickable; PR items without URLs are disabled or not clickable.
6. The user reviews `Activity Timeline`.
7. If no activity exists, the timeline shows `No activity logs available.`
8. If review actions apply to a done task, footer actions such as `Approve Workspace` or `Approve Repo` may be shown.

Expected result: the user can understand task state, execution state, PR state, and history without reading raw files.

### Journey 20 - Copy task ID

1. The user opens a task tab.
2. The user clicks the copy icon next to the task title.
3. The task ID is copied.
4. The icon changes to a copied state for a short time.
5. The icon returns to the default copy state.

Expected result: the user can quickly copy a task ID for chat, PRs, issues, or documents.

### Journey 21 - Open task chat

1. The user is in a task tab.
2. The user clicks the chat action in the task header.
3. Agent chat opens on the right.
4. Task content remains visible on the left.
5. The default split is 50 percent task content and 50 percent chat.
6. The chat header uses the task title as the main title.
7. The subtitle uses short task context, such as task ID plus parent feature or current status.
8. The composer placeholder is short and task-specific.

Expected result: the user can ask questions in the current task context.

### Journey 22 - Close or back out of a task tab

1. The user clicks `X` on a task tab.
2. The tab is removed from the header.
3. If the closed tab was active, the app activates the nearest useful tab or returns to the workspace board when no work item tab remains.
4. If the closed tab was not active, the active tab does not change.
5. If the user clicks Back inside a task tab opened from a feature tab, the app returns to the parent feature tab.
6. If no parent feature tab context exists, Back returns to the workspace board.

Expected result: leaving a task tab does not lose the workspace and preserves the most relevant parent context.

### Journey 23 - Activate a feature tab

1. A feature tab exists in the header.
2. The user clicks the feature tab.
3. The feature tab becomes active.
4. The main content changes to the feature detail session.
5. The sidebar is hidden.
6. If agent chat is open, chat scope follows the feature.

Expected result: the user returns to the exact feature session represented by the tab.

### Journey 24 - Read feature tab header and stage state

1. The user opens a feature tab.
2. The feature tab header shows:
   - Back action.
   - Feature title.
   - Copy feature ID action.
   - Feature status pill.
   - Current stage pill.
   - Modified time when available.
   - Short active-view summary when useful.
   - Agent chat open action when chat is closed.
3. The user hovers or opens the current stage pill.
4. A stage popover shows `Product spec`, `Technical design`, `Tasks`, and `Handoff` in workflow order.
5. Approved stages are visually marked as complete.
6. The current stage is visually highlighted and labelled current.
7. Draft or future stages are visually muted.
8. The popover closes when the user leaves the control or dismisses it.

Expected result: the user can understand the feature stage state without opening raw `status.yaml`.

### Journey 25 - Switch feature tab views

1. The user is in a feature tab.
2. The tablist shows source-backed views:
   - `Product Spec`.
   - `Technical Design`.
   - `Tasks`.
   - `Logs` or `Status/Logs`.
3. Product Spec and Technical Design show a completion indicator when the corresponding source has been completed or approved.
4. The active view is highlighted.
5. The user clicks another view tab.
6. The content changes without closing the feature tab.
7. Agent chat, if open, keeps feature scope and updates the active-section subtitle.

Expected result: the user can browse all feature source and state views inside one feature session.

### Journey 26 - Read Product Spec and Technical Design views

1. The user opens the `Product Spec` view.
2. The app shows the source file label, such as `SOURCE product-spec.md`.
3. The markdown renders as readable document preview with headings, paragraphs, lists, links, inline code, and code blocks.
4. The user switches to `Technical Design`.
5. The app renders `technical-design.md` as readable document preview.

Expected result: the user can read feature source documents without leaving the dashboard.

### Journey 27 - Use the Tasks view inside a feature tab

1. The user clicks `Tasks` in the feature tab.
2. The content shows `Feature tasks` and a total task count.
3. Each task item shows task ID, status, title, repository when available, branch when available, latest activity when available, and next action or blocked reason when available.
4. The user clicks a task item.
5. The app opens or focuses the corresponding task tab.
6. The task tab becomes active.
7. When the user clicks Back from that task tab, the app returns to the original feature tab and preferably restores the `Tasks` view.

Expected result: the user can drill down from feature context to task context and return to the original feature session.

### Journey 28 - Use Logs or Status view inside a feature tab

1. The user clicks `Logs` or `Status/Logs`.
2. The content shows feature-level activity or status history.
3. Each item shows action, stage when available, actor, timestamp, and note when available.
4. If no logs exist, the view shows `No feature logs are available.`

Expected result: the user can understand feature history without opening raw status files.

### Journey 29 - Copy feature ID

1. The user opens a feature tab.
2. The user clicks the copy icon next to the feature title.
3. The feature ID is copied.
4. The icon changes to a copied state for a short time.
5. The icon returns to the default copy state.

Expected result: the user can quickly copy a feature ID for chat, PRs, issues, or documents.

### Journey 30 - Open feature chat

1. The user is in a feature tab.
2. The user clicks the chat action in the feature header.
3. Agent chat opens on the right.
4. Feature content remains visible on the left.
5. The default split is 50 percent feature content and 50 percent chat.
6. The chat header uses the feature title as the main title.
7. The subtitle uses feature ID and the active feature view, such as `Product Spec`, `Technical Design`, `Tasks`, or `Logs`.
8. The greeting is short and focused on the current feature.
9. No long scope card appears at the top of the chat.

Expected result: the user can ask questions in the current feature context.

### Journey 31 - Close a feature tab

1. The user clicks `X` on a feature tab.
2. The feature tab is removed from the header.
3. If the closed tab was active, the app activates the nearest useful tab or returns to the workspace board.
4. If task tabs related to the feature exist, they remain open unless a future product decision explicitly introduces cascade close.

Expected result: closing a feature tab does not remove unrelated task sessions or change the workspace.

### Journey 32 - Start a new chat in the same scope

1. The user opens agent chat from a task or feature tab.
2. The user clicks `New chat`.
3. A new chat session starts in the same task or feature scope.
4. The session title is `New Chat`.
5. The composer is empty.
6. Attachments are empty.
7. The default model is `GPT-5.5` unless a session-specific choice already exists.
8. A short greeting appears.
9. The new session becomes active.

Expected result: the user can start a fresh conversation without leaving the current task or feature context.

### Journey 33 - Send the first message in a new chat

1. The user types a message.
2. The user clicks Send or presses Enter when no mention menu is active.
3. The user message appears in the message list with a timestamp.
4. The composer clears.
5. The chat session title updates from the first message text.
6. The UI prepares a future API payload containing the message, selected model, and scoped task or feature context.
7. If the real chat API is not connected, no fake assistant message or fake typing indicator appears.

Expected result: user messages are captured and scoped context is ready for future backend integration.

### Journey 34 - Write multiline chat input

1. The user types in the composer.
2. The user presses Shift + Enter.
3. The composer inserts a new line.
4. The message is not sent.

Expected result: Enter sends a message, while Shift + Enter writes multiline input.

### Journey 35 - Resize and expand chat

1. Agent chat is open beside a task or feature tab.
2. The user drags the chat resize handle.
3. Dragging left makes chat wider.
4. Dragging right makes chat narrower.
5. The split updates while dragging and keeps usable minimum and maximum widths.
6. The user clicks fullscreen or expand.
7. Chat becomes wider or fullscreen.
8. The user clicks minimize or presses Escape.
9. Chat returns to its previous size.

Expected result: the user can control available reading and writing space without losing chat state.

### Journey 36 - Choose a model

1. The user opens the model selector in the composer toolbar.
2. A menu opens above the selector.
3. The menu lists:
   - `GPT-5.5` - `Extra High`.
   - `GPT-5.4` - `Balanced`.
   - `GPT-5.4 Mini` - `Fast`.
   - `GPT-5.3 Codex` - `Code`.
4. The selected model is marked.
5. The user clicks a different model.
6. The model is applied to the active chat session.
7. The menu closes.
8. Clicking outside or pressing Escape closes the menu without changing the model.

Expected result: model selection is clear and scoped to the current conversation.

### Journey 37 - Mention a workflow skill with `$`

1. The user focuses the composer.
2. The user types `$`.
3. A `Skills` mention menu opens above the composer.
4. The menu includes:
   - `$resume-feature` - `Summarize feature state`.
   - `$init-feature` - `Create a new feature folder`.
   - `$approve-feature` - `Approve current workflow stage`.
   - `$tech-lead` - `Generate design and task structure`.
   - `$start-implementation` - `Begin an executable task`.
   - `$pr-create` - `Create PR and update task metadata`.
   - `$pr-self-review` - `Review implementation before handoff`.
   - `$list-features` - `List workspace feature state`.
5. The user types a query such as `$pr`.
6. The menu filters by skill value or description.
7. The user clicks an option or presses Enter while the menu is active.
8. The trigger text is replaced with the full skill mention and a trailing space.
9. Composer focus remains active.

Expected result: the user can reference workflow skills quickly in a prompt.

### Journey 38 - Paste an image attachment

1. The user copies an image to the clipboard.
2. The user pastes into the composer.
3. The app detects the image.
4. A preview appears above the textarea.
5. The user may remove the attachment before sending.
6. When the user sends the message, the image is attached to the user message and cleared from the composer preview.

Expected result: the user can send screenshots or visual context to the future agent endpoint.

### Journey 39 - Close and restore chat

1. The user clicks the close chat action.
2. The chat panel closes.
3. The active chat session remains associated with the current task or feature scope when persistence is available.
4. Reopening chat in the same scope can restore messages, selected model, and draft state when product persistence is enabled.

Expected result: closing chat removes the panel from view without intentionally discarding scoped conversation state.

## Data Expectations

- Workspace, feature, and task data must come from imported workspace data, not hardcoded mock data.
- Feature chat context should include feature ID, feature title, active section, product spec, technical design, tasks, logs, and status data when available.
- Task chat context should include task ID, task title, parent feature, status, next action, blocked reason, blocked context, PR state, handoff state, and activity when available.
- Missing optional values should render as explicit empty states such as `None`, disabled links, or empty-state copy.
- Chat persistence should be scoped by workspace plus feature for feature chat, and workspace plus feature plus task for task chat.
- Duplicate or cloned sessions, if supported, must not overwrite the original task or feature chat session.

## Accessibility and Keyboard Expectations

- Workspace switcher, context menus, tabs, chat controls, model selector, and mention menus should be keyboard accessible.
- Workspace switcher and context menus close on outside click or Escape.
- Work item tabs expose active state to assistive technology.
- Icon-only actions have clear accessible labels.
- Fullscreen chat exposes pressed or expanded state.
- Send is visibly and programmatically disabled when there is no message text and no attachment.
- Enter selects the active mention while a mention menu is open; Enter sends only when no mention menu is active.

## Acceptance Criteria

- A user can click the workspace tab from any task or feature tab and return to the current workspace board.
- A user can open the workspace switcher from the workspace tab dropdown, search saved workspaces, switch workspace, and close the switcher without side effects.
- A user can open the import workspace modal from the switcher and submit repository URL plus GitHub token.
- Import errors keep the modal open, show a clear error, and clear the error when the user edits inputs.
- Single-clicking a task opens task quick view without creating a task tab.
- Double-clicking a task opens or focuses the corresponding task tab.
- Right-clicking a task opens a context menu with `New tab`.
- Task sidebar items support the same single click, double click, and right click behavior as task cards.
- Single-clicking a feature opens feature quick view.
- Double-clicking a feature opens or focuses a feature tab only in Feature Mode.
- Right-clicking a feature in Feature Mode opens a context menu with `New tab`.
- Task tabs and feature tabs show type indicators, labels, active state, close controls, and correct fallback behavior after close.
- Sidebar is visible only on the workspace board and hidden in task and feature tabs.
- Task tabs show task metadata, blocked state, dependency state, PR state, and activity timeline.
- Feature tabs show header stage state, source-backed views, markdown previews, tasks list, and logs/status history.
- Opening a task from a feature Tasks view creates or focuses a task tab, and Back returns to the originating feature tab when that context exists.
- Agent chat opens only in task or feature scope, never as a standalone workspace-board chat.
- Agent chat opens beside the active task or feature content with a default 50 percent / 50 percent split.
- Agent chat can be resized, expanded, minimized, closed, and reopened without intentionally losing scoped session state.
- `New chat` creates a fresh chat session in the current task or feature scope.
- Model selection applies to the active chat session.
- `$` skill mentions can be inserted from the composer menu.
- Text send, multiline input, disabled send state, timestamps, and pasted image attachments work as described.
- Before a real chat API exists, sending a message does not create mock assistant responses or fake typing state.
- The UI prepares selected model and scoped task or feature context for future chat API integration.
